# 評価パイプライン設計プレイブック

出典：Chip Huyen『AIエンジニアリング』4章（4.1〜4.4）の要点を、設計作業の手順として再構成したもの。

## 評価駆動開発

作る前に評価基準を決める。評価基準は4つに分けられる。

| 分類 | 何を測るか | 主な手法 |
|---|---|---|
| ドメイン固有の能力 | その領域の問題を解けるか | 多肢選択、機能正確性（コード実行等） |
| 生成能力 | 事実整合性、安全性 | AI as a Judge、SelfCheckGPT、含意分類器、有害性分類器 |
| 指示追従能力 | 形式・制約に従えるか | IFEval型の自動検証、チェックリスト判定 |
| コストとレイテンシー | 品質とのトレードオフ | パレート最適化。必須要件で絞ってから最良を選ぶ |

ドメイン能力はプロンプトの小さな違いで結果がぶれるので、複数のプロンプト表現で測る。

## モデル選定の4ステップ

1. 変えられないハードな属性（ライセンス、オンプレ必須、言語など）で除外
2. 公開情報（ベンチマーク、リーダーボード）で絞り込み
3. 独自評価で選ぶ
4. 本番で監視し、繰り返す

公開ベンチマークは足切り用。選び方や集計方法がばらばらで、相関の強いベンチマークを重ねるとバイアスになる。データ汚染もある。**モデル選定とは自分用のリーダーボードを作ること**。

## ステップ1：全コンポーネントを評価する

### 例：履歴書PDFから現職を抽出するアプリ

```
PDF ──[抽出]──▶ テキスト ──[抽出]──▶ 勤務先
       評価①                 評価②           評価③（最終）
```

- 評価①：テキスト抽出の正確さ（文字化け率、レイアウト崩れ）
- 評価②：正しいテキストが入力されたときの勤務先抽出精度
- 評価③：PDFから勤務先までの最終精度

①と②を分けておくと、③が下がったときにどちらが原因か即座に分かる。

### ターンベースとタスクベース

- ターンベース：1回1回の出力の品質
- タスクベース：課題を最後まで解けたか、何往復かかったか（BIG-benchのtwenty_questionsは何問で正解したかで採点する）

ユーザーにとって重要なのはタスクベース。2ターンで解決と20ターンで解決は体験がまるで違う。エージェントなら「ツール呼び出しの正しさ」（ターン）と「最終的な目標達成」（タスク）を分ける。

## ステップ2：評価ガイドラインを作る

### スコープ外を定義する

何をすべきかだけでなく、何をすべきでないかを書く。扱わない入力に対する正しい振る舞い（断る、誘導する）も評価対象。

### 「正しい」と「良い」

LinkedInの求人マッチングでは「あなたは全く不適格です」という回答は正しいが悪い回答とされた。良い回答は、足りない点とその埋め方まで伝える。ルーブリックには「正しいが悪い」例を必ず入れる。

### 評価基準の数

典型は2〜3個（関連性、事実整合性、安全性）。基準が多いと、採点者の負担と指標間の相関が増えて意味が薄れる。

### 採点方式とルーブリック

- 2値（合格/不合格）：判断が速い、CIゲートに向く
- 5段階：差を見たいとき。ただし3と4の境界が曖昧になりがち
- −1/0/1：改善・変化なし・悪化を見るとき

ルーブリックは各スコアに例を付け、**他の人にも採点してもらって分かりにくいところを直す**。採点者間の一致が低いルーブリックは、ジャッジに渡しても一致しない。

### ビジネス指標との対応付け

例：事実整合性80%なら問い合わせの30%を自動化でき、98%なら90%を自動化できる。この表があると、評価への投資額を経営判断に接続できる。「これ以下なら使い物にならない」最低ラインも決める。

## ステップ3：評価手法とデータを決める

### 手法の使い分け

| 基準 | 手法 | コスト |
|---|---|---|
| 有害性 | 専用の小さな分類器 | 低 |
| 関連性 | 意味的類似度 | 低 |
| 形式・制約 | 決定的チェック（正規表現、スキーマ検証） | 最低 |
| 事実整合性 | AI as a Judge | 高 |
| 総合的な良さ | 人手評価 | 最高 |

安い手法で全件、高い手法で1%、のように組み合わせる。

### logprobs

logprobsが取れるなら、出力の確信度として使える。分類タスクでは確信度の低い出力だけを人手に回す、という使い方ができる。

### 人手評価

今でも開発の方向を決める最重要指標になり得る。LinkedInは1日最大500件の会話を人が評価していた。全自動化を目指すのではなく、人手評価を「校正用アンカー」として常設する。

### スライス

本番データにアノテーションを付け、グループごとに評価する。目的は3つ。

1. バイアスの発見（特定ユーザー層で性能が低い）
2. デバッグ（どの入力タイプで壊れるか）
3. シンプソンのパラドックスの回避

シンプソンのパラドックス：どのグループでもAのほうが成績が良いのに、全体ではBが勝つ現象。グループ間でサンプル数が偏っているときに起きる。全体平均だけ見ていると、悪いほうを選ぶ。

### 評価セットは複数用意する

- 本番の分布に沿ったセット
- 間違いやすい例（ハードケース）
- タイプミス・表記ゆれ
- スコープ外の入力

### サンプル数

OpenAIの目安：検出したい差が1/3になるごとに必要サンプル数は10倍。

| 検出したい差 | 必要件数 |
|---|---|
| 30% | 約10件 |
| 10% | 約100件 |
| 3% | 約1,000件 |
| 1% | 約10,000件 |

ブートストラップ（評価セットからランダムに抜き直して何度か採点）でスコアが大きくブレるなら件数が足りない。

## パイプライン自体を評価する

- 良い回答に高いスコアがつくか
- 再現性：2回実行して同じ結果になるか（AI as a Judgeはtemperature=0）
- 指標同士の相関：高相関なら同じものを測っている
- 評価が追加するコストとレイテンシー

評価データ、ルーブリック、ジャッジのプロンプト、サンプリング設定をすべて記録する。実験追跡はマイグレーション履歴のようなもの。

## Webエンジニア向けの対応表

| 評価パイプライン | Web開発の対応物 |
|---|---|
| コンポーネント評価 | ユニットテスト |
| タスクベース評価 | E2Eテスト |
| ルーブリック | 受け入れ条件（Acceptance Criteria） |
| ビジネス指標との対応付け | SLOをKPIに結びつける |
| スライス分析 | ダッシュボードのセグメント別表示 |
| サンプル数の表 | A/Bテストの検出力計算 |
| 評価設定のログ | 実験管理、マイグレーション履歴 |
